## 1. What the compile server costs to run (measured here)

Container of this session: 4 vCPU, 16 GB. `atmos-web`, emcc 7.0.1, lang
d76b547, `-O2`. "Largest process" is the biggest single process of the
build (`ru_maxrss` of the children), not the sum of the processes alive
at once, which was not measured.

| Page | Libraries cached, 1 core | Libraries cached, 4 cores | Libraries not cached, 4 cores / 1 core | Largest process |
|---|---|---|---|---|
| web (DOM) | 1.4 s | 1.0 s | not measured | 112 MB |
| text (print and time) | 1.6 s | not measured | not measured | 107 MB |
| pico (canvas, Asyncify) | 16.3 s | 5.5 s | 8.6 s / 19.3 s | 222 to 250 MB |

- The pico page is the heavy one: about 16 CPU-seconds, almost all of
  it in the Asyncify step of the linker. The pages of the guides are
  built ahead, so this cost only matters for an edited program.
- Disk: emsdk 2.1 GB (906 MB of it is the cache of the SDL ports), plus
  3.5 MB per pico page (and the assets of the program), 0.2 MB per text
  page. Plan 5 GB free at least, and a rule to prune the pages kept.
- Needs: glibc 2.28 or newer (the node of emsdk; clang needs 2.18),
  root (or a user with room for 2 GB), no limit on processes.
- One earlier run of a web page on 1 core took 32 s of wall time for
  4 s of CPU: a first-run effect (not repeated in the next 3 runs).
- Not measured: a cheap shared-CPU VPS may be slower than this
  container; the peak memory of a whole build; many builds at once.

## 2. Freechains (read from `Freechains/freechains.vcs`, fetched today)

| Question | What the pages say |
|---|---|
| Made of | "implemented in Lua (>=5.4) on top of Git"; installed with LuaRocks; apt: `git openssh-client lua5.4 luarocks` |
| Run | `freechains daemon start [--port=<port>] [--hub]`; "Serving on port 8330"; a long-running process (the docs background it with `&`) |
| Peers | synchronization "is always explicit and peer-to-peer through `recv` (or `send`)"; `--hub` accepts `send` from peers |
| Inbound | NOT STATED. By the design, one who wants others to pull from it needs a port they can reach (an inference, not a quote) |
| Data | `~/.freechains/`; each chain is a Git repository, each action a commit; `sweep` compacts |
| RAM, disk growth, bandwidth | NOT STATED |
| State | the page says "Stable branch is v0.20"; the CLI says v0.21; no releases or tags; the old JVM versions are not the current one |
| Container, VPS, Raspberry Pi | NOT STATED |

So a Freechains node is light (Lua and Git), but it is a process that
stays up, on a TCP port that others reach. A browser cannot speak that
protocol (a `git daemon` over TCP): a page needs an HTTP bridge on the
server that calls the `freechains` command.

## 3. What each part needs

| Part | Where it can live | Why |
|---|---|---|
| The static site (guides, landing, demos) | anywhere, including the shared DreamHost | files only |
| The compile server | a machine with root, 2 GB of disk for the tools, glibc 2.28+, and room for a compile of about 16 CPU-seconds | measured above |
| A Freechains node (and a bridge to the page) | a machine with a process that stays up and a TCP port open | the daemon |

The shared plan ("Shared Unlimited") is likely to fail the last two
(a persistent process, an open port, memory limits); the quick stage of
`site/probe.sh` shows it in 1 minute.

## 5. A possible layout

- Static files on the current hosting (or on the VPS).
- One VPS with: the compile server (behind a rate limit, a size limit
  and a timeout), a Freechains node, and a small HTTP bridge for the
  pages.
- A subdomain for it (for example `build.ceu-lang.org`), with the right
  CORS headers for the pages that call it.
- A setup script and a service file, so that the machine is rebuilt
  from the repository.

## Result of probe-node.sh on the shared host (2026-11-27)

- The `node` of the system (v18) runs. The `node` of emsdk (v24) dies at
  start (V8 `SetPermissions`, kernel grsec, PaX flags `PeMR`); with
  `--jitless` it runs. `emcc` works with a wrapper that adds `--jitless`
  (`EM_NODE_JS`).
- The pages did not build only because lang now requires `:prelude.c` or
  `:prelude.h`; `web.atm` and `clock.atm` were changed to `:prelude.c`.
- Second run (clones updated): the three pages build on the host with
  `node --jitless`: web 3 s, text 3 s, pico (heavy) 9 s, 3 wasm files,
  no process killed. Compiling on the shared DreamHost is possible.
- Open: limits of a compile server there (CPU time and memory of a
  shared account, a CGI/FastCGI process, concurrency).

## A correction (2026-11-27, the author asked "a compilação de Céu funciona; por que Atmos não?")

Section 3 above said the shared plan was likely to fail for the compile
server. The probes say otherwise: the three pages of env-web build on the
shared host with `node --jitless` (web 3 s, text 3 s, pico 9 s, nothing
killed). And the author compiles and runs Céu programs there, a request
at a time, with no process that stays up. So the compile server may be
a program run per request (CGI, PHP) on the shared plan. Still open for
it: the CPU and memory limits of the host under a real request, and
isolation (a program with native C blocks can `#include` a file of the
host and read it back in an error message). What really needs a process
that stays up and an open port is the Freechains node: that is what
`site/probe-daemon.sh` tests.
